# Implementation and research checkpoints

Keep implementation in Python modules and use notebooks as launchers. Use the
existing isolated checkout; no new Git worktree is needed for this workflow.
Each ticket records allowed files, public interfaces, independently calculated
acceptance expectations, executable commands, artifacts, and remaining limits.

## Required checkpoint report

- Code/configuration/model identity and artifact locations.
- Passed, failed, skipped, and unrun checks, including the underlying command exit status.
- Completed games, infrastructure errors, pending/duplicate instances, and usage completeness.
- A diagnosis supported by prompts/traces and a proceed/fix/revise decision.
- A clear statement of what remains unverified. Tests of random/fake models do not validate Qwen capability.

## Scientific acceptance criteria

Define good results as trustworthy and informative, including null results.
Never require a preferred memory format to win as an implementation gate.
Use development seeds to calibrate prompts, difficulty, budget, and memory
pressure. Keep held-out seeds untouched until the protocol and analysis freeze.

Pilot analysis should examine full-history/no-memory diagnostics, exact memory
utilization, fact retention, reread opportunities and affordability, completion,
budget exhaustion, invalid output, repair costs, runtime, and billed compute.
Fewer rereads alone can reflect either effective memory or failure to recover.
The current simple game defaults are integration fixtures; they do not establish
that the task requires difficult memory management.

For completion, the primary research interaction can be written as
`(structured_5 - prose_5) - (structured_2 - prose_2)`, with the corresponding
hybrid contrast. Prespecify the primary outcome and contrast(s), treatment of
multiple comparisons, a practically meaningful effect, and retry/exclusion
rules. Keep recipe rereads, score, budget, inference tokens, and runtime in the
analysis; document any changes from the proposal's primary metrics.

Bootstrap whole matched game instances with all conditions together. Do not
treat actions as independent samples. Twenty instances per condition gives
coarse completion rates and potentially wide interaction uncertainty; use
pilot-informed simulations over several plausible effects to assess sensitivity.
Report inconclusive results when uncertainty cannot distinguish meaningful
effects from negligible ones. A small pilot's observed effect is not a stable
single estimate for power planning.
