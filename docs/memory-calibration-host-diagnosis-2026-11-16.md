# Calibration host resource diagnosis

November 16, 2026. Read-only investigation after two JSON-seed-1 startup OOM kills. No additional Qwen launches, process termination, disk cleanup, WSL restart or configuration changes were performed.

**A concrete storage problem is established:** Windows C: has only 15,507,456 bytes available (about 15 MB), reported as 100% full. Linux root reports about 767 GiB free; this does not describe the separate Windows C: volume. WSL configuration specifies memory=12GB and swap=8GB. `/dev/sdc` is the active 8-GiB swap device. Two `swap.vhdx` files were found under the Windows user's Temp subdirectories on C: (approximately 0.69 and 6.50 GiB physical file sizes). The exact active candidate was not identified, but both are on the full volume. Microsoft's [WSL configuration reference](https://learn.microsoft.com/en-us/windows/wsl/wsl-config) documents disk-backed swap and the default Temp swap-file location.

The existing kernel snapshots confirm global host-RAM OOM, free swap=0 at both kills, and swap-device write errors. In the first failed load, Qwen had approximately 2.17 GiB resident and 4.66 GiB of swap entries; the other model server had 0.52 GiB resident and 2.65 GiB of swap entries. At the second failure Qwen had approximately 2.21/4.14 GiB resident/swap entries, and the other server 0.52/3.17 GiB. These are point-in-time kernel accounting values, not peak-memory measurements. Swap entries do not prove corresponding disk writes succeeded; swap-cache pages and failed writes make simple addition to resident usage an incomplete description of physical memory.

The successful and failed JSON manifests have identical model/runtime settings, and the same frozen source digest. The two game seeds load identical weights, with gameplay beginning only after model loading. Original GPU preflight recorded 875 MiB occupied; later inspections recorded about 7,010 MiB, and another model server was present at both OOMs. However, some successful recovery runs also coexisted with that workload, so its presence alone does not explain the transition.

**Supported diagnosis:** the full Windows volume is a strong explanation for swap write failures, leaving the limited/shared WSL RAM unable to accommodate model-loading pressure. This is more specific than merely saying a restart might help. Advertised free swap slots are not reliable usable capacity if the backing storage cannot accept writes.

**Historical uncertainty:** no RAM/swap/Windows-free-space time series was captured during successful loading peaks, and no sysstat/atop history was found. Swap errors exist earlier in the boot as well; they cannot be described as newly appearing specifically at JSON seed 1. We cannot establish when C: filled or precisely which resource change separated the last success from the next failure. The exact Windows storage-error code and active swap-VHD identity remain unverified. Raw kernel wall-clock labels can shift; use the preserved attempt UTC times for user-facing run chronology.

Next address Windows disk space, verify swap/backing-storage health, then reassess a single unchanged baseline retry. A WSL restart by itself does not free Windows disk space or establish that storage is repaired. Increasing only the nominal swap setting would not solve a full backing volume. No files or workloads have been selected for deletion or stopping by this investigation.
